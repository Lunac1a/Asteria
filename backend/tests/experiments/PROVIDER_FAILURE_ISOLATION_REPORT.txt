Root cause / minimum proposal (not implemented)
- Confirmed missing guarantee: killing actual caller does not clean Provider descendants.
  The outer wall-clock deadline lives in that caller; after it dies it cannot enforce it.
  The child memory-only Job does not tie its lifetime to caller survival. SDK read timeout
  is not a complete-response deadline when the server continually makes read progress.
- Minimum candidate: caller-owned, non-inherited KILL_ON_JOB_CLOSE Job per Provider
  invocation; atomic process assignment including launcher descendants; retain memory cap,
  credential stdin boundary, allowlist/no redirects, SDK retry policy and existing chat_slot.
  On timeout terminate the tree, boundedly verify captured handles AND Job membership count,
  then boundedly finish/close IPC. Failure to confirm cleanup must remain an explicit failure.
- Existing Windows helper is mechanically compatible in outer-containment experiment;
  integrating it directly into Provider still needs targeted tests, bounded IPC design and
  unsupported-platform fail-closed behavior. No implementation or limiter change this round.

Limits / evidence quality
- NO infinite wait reproduced while caller alive. Source-level unbounded second communicate
  remains a portability/other-descendant risk, not a demonstrated failure in this environment.
- Parent-crash survivors observed beyond configured6 sec; forcibly removed at8 sec after
  crash. This is real orphaned resource retention, not proof of infinite lifetime.
- External safety Job, Windows venv launchers and this Python build define tested topology;
  no claim for other Windows/Python builds, arbitrary subprocess descendants or Linux.
- Isolated caller used as permitted by task; FastAPI health/readiness not exercised.
- No CPU/RSS benchmark, handle-object inventory, long-run leak or concurrency capacity claim.
