Method and environment
- Windows11 build26300, CPython3.12.10, i9-13980HX (24 cores/32 logical processors),
  physical RAM31.62 GiB; roughly11.74 GiB available at hardware snapshot, not reserved.
- One isolated caller process with1 or2 threads calling real generate_response directly.
  No FastAPI/Chat path bypass claim: this explicitly tests independent Provider capacity,
  while production HTTP Chat remains serialized by chat_slot.
- Real disposable launchers, actual Python processes, Job ownership, memory guard and SDK.
  Local OpenAI-compatible HTTP mock only; synthetic credentials/config, empty cwd.
- Thread Barrier coordinates invocation start. Server waits until ALL requests arrive;
  only then observe a fixed2-second holding interval and release. This proves overlap by
  events rather than probabilistic scheduling. Total latency includes that deliberate hold.
- Normal order1,2,2,1,1,2: three batches per level,3 and6 successful calls respectively.
  Then timeout and caller-crash cases at each level, one batch each. Fresh caller per batch.
- Resource sampler every~100ms; OS GetProcessMemoryInfo measures WorkingSet/RSS and
  PrivateUsage/Private Bytes, Toolhelp measures threads, GetProcessHandleCount handles,
  GetProcessTimes process CPU. Native Job accounting supplies lifetime user+kernel CPU
  across ALL Provider members, including exited members. CPU seconds are not wall time.
- Provider trees are separated from caller scaffolding and observer/mock. Each call had
  venv launcher + actual Python + conhost (3 processes). Safety outer Job remained open;
  finite22-second external Watchdog and explicit final cleanup protect the experiment.

- Latency change+77.7ms (+2.13%); per-call CPU+5.30%. With only three batches/level,
  cold imports, ordinary host background activity and instrumentation, these do not
  establish a statistically significant resource-contention penalty.
- RSS and Private Bytes approximately2x; process count exactly2x. Summed RSS may count
  shared resident pages more than once; it is NOT incremental system physical memory.
  Private Bytes measures private committed memory, not just resident memory.
- Peak values are sampled maxima, not guaranteed instantaneous peaks; different metric
  maxima need not occur at the same timestamp. No instantaneous CPU utilization SLA.

Correctness, fault and cleanup observations
- Normal:9/9 calls returned exact OK; expected HTTP arrivals per batch, one SDK request
  each. Every completed Provider Job reported active0, caller quarantine0, IPC gone.
- Timeout:1 call at6.016sec;2 concurrent calls each6.031sec, all provider_timeout. Mock
  trickles incomplete JSON every200ms so SDK read-idle timer cannot preempt outer deadline.
- Caller crash: all captured process handles signaled within~31ms (1) /15ms (2).
  Native outer Job active0 BEFORE safety cleanup; actual Provider processes included.
- All10 batches: native cleanup reached active0, captured handles exited, observer pipe
  reader joined, no Watchdog fired. No external intervention was needed for native exits.
- Two sampler queries raced normal process exit and are recorded as sampling_race, not
  replaced with zeros. Barrier-held sampling and OS cleanup checks remained available.
- CPU accounting is complete for normal/timeout. Crash case child-side Job accounting
  cannot emit after caller death: summary cpu_complete=false and numeric0 is a placeholder,
  NOT a measured zero CPU cost; raw pre-crash process CPU samples remain available.

Interpretation and next step (inference, not verified Chat capacity)
- This workstation showed no demonstrated Provider resource bottleneck or ownership defect
  at2 calls, and resource growth was approximately proportional. It supports advancing to
  a controlled2-independent-Session end-to-end experiment once the intended coordination
  change is separately reviewed and authorized. It does NOT authorize opening chat_slot.
- Stop at2 for this stage.5-call testing is not necessary to resolve the next question:
  Session/workspace state correctness plus shared Retrieval/Embedding and DB behavior under
  real Chat overlap. Raising isolated Provider load would not validate those invariants.
- Do not infer maximum concurrency, long-run leak freedom, production rate-limit handling,
  remote network performance, or behavior on smaller machines/other Windows/Python builds.
  Fixed tiny responses and moderate2-second holds do not cover maximum payloads or slow
  paid APIs. Existing1536MiB per-process cap is not an aggregate Provider memory budget.
- Parent still incurs per-call execution/IPC threads and handles; sampling itself has some
  overhead. No uninstrumented comparison or repeated long-lived-caller leak study this round.
