Deterministic sequence and verified observations
All four requests omit session_id and use one fixed UUID request_id (recorded in JSON).
A reaches the Mock LLM and signals entered; it cannot continue until release is set.
The controller waits for entered, sends B and reads an independent DB snapshot before
releasing A. No sleep is used to manufacture the overlap. All waits have deadlines.

The replay response equals A's entire response, including the newly created Session ID.
LLM calls across the complete sequence: exactly 1.
A executes retrieval -> LLM -> commit_returned -> Session close.
Concurrent B, replay and conflict requests have Session open/close events but no
Retrieval, LLM or Commit events. These measurements describe this execution only,
not performance distributions or throughput.

Meaning of the guarantee under tested conditions
Current chat_slot serializes admission before the ChatTurn lookup:
backend/app/api/routes/chat.py:46 acquire; :51 lookup; :65 conflict; :66 replay.
Session is allocated only after generation (:222); turn inserted :290; commit :299;
finally releases slot :302. ChatTurn.request_id is a global primary key:
backend/app/models/chat_turn.py:10.
Therefore the overlapping duplicate is rejected rather than joined to A. Only after
completion can B reuse persisted results. This is fail-fast mutual exclusion plus
persisted replay, not in-flight result sharing or a guaranteed exactly-once external
provider call across crashes, lost commit acknowledgements or retries after failure.
