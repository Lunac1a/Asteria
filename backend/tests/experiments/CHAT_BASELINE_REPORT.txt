Environment and workload
Production sources unchanged this turn. Existing uncommitted knowledge.py User
row-lock fix and prior experiment files retained. Per-run source hashes saved.
Python 3.12.10 on Windows 11, 32 logical CPUs; SQLAlchemy 2.0.49, Uvicorn 0.44.0.
PostgreSQL 16.15 runs in a dedicated WSL Ubuntu cluster, READ COMMITTED.
Default QueuePool: size 5, overflow 10, timeout 30s, recycle -1, pre_ping false,
reset-on-return rollback. No pool/semaphore sizing changes. Test-only DB
connect/statement/lock timeouts 5/8/4 seconds. One Uvicorn worker; sequential
requests via one persistent loopback HTTP client; HTTP timeout 45 seconds.
Runtime metrics and optional citation-audit calls disabled in synthetic settings.
No maintenance or Startup Recovery. No developer DB or real user records.

Each run: 5 warmups, then 50 measured requests. A second identical run was
selected because the first run's ten-request batch means varied materially.
The two runs use separate fresh databases, not parallel servers. No outliers
are removed; warmups are saved but excluded from reported distributions.
One synthetic user, workspace, document and one indexed chunk. Every request
has a unique request_id and its own questioning Chat Session with the same
two-message initial history; same question, configuration and retrieval corpus.
Rows accumulate across requests but per-session context remains fixed.

Real paths and mock scope
Real JWT validation/user lookup, history loading, language policy, routing,
retrieval query, query embedding subprocess, scoring, prompt assembly, provider
configuration/decryption, response parsing/citation checks and persistence.
Real offline FastEmbed model: sentence-transformers/paraphrase-multilingual-
MiniLM-L12-v2, local ONNX cache copied to isolated temporary storage; file hashes
saved. Retrieval threshold 0.35, lexical rescue enabled. Both index preparation
and every query use the real worker. No embedding mock or cached query vector.
Only completion.generate_response is replaced with deterministic JSON text at
the external-provider boundary. LLM_BACKEND=provider avoids the built-in test
shortcut. No real provider HTTP call, paid call or provider transport measured.
The fixed mock returns a grounded answer citing source 1; application validation
is unchanged. Smart routing uses the normal explicit-evidence guard, not the
intent-classifier LLM branch. No learning/adaptive-session path in this baseline.

Timing definitions (monotonic perf_counter, test-only wrappers)
HTTP: immediately before client.post through complete response receipt.
Routing: real decide(). Retrieval: real retrieve(), including query embedding.
Embedding worker (nested): real run_worker(), including subprocess creation,
imports/model initialization, inference and IPC; not pure inference latency.
Prompt preparation: grounded_answer entry to provider_completion invocation.
Provider wrapper: real provider_completion, including config read/decryption,
transaction rollback, mocked generation and return.
LLM mock (nested): deterministic mock validation, serialization and return.
Answer validation/composition: provider_completion return to grounded_answer
return. Includes real parsing, citation checks and answer composition.
Post-generation/persistence: grounded_answer return through final commit return;
includes source revalidation, ORM writes/flushes, ChatResponse construction and
ChatTurn commit. It is NOT a pure database-write metric.
Commit (nested): final Session.commit() only; earlier flushes are outside it.
Other HTTP: residual outside the non-overlapping stages. Includes authentication,
history/language/context loading, middleware, transport and response serialization.
Full context preparation and FastAPI response-model validation are NOT reliably
isolated here; no standalone numbers are invented. Pool wait is not measured.
Nested rows must not be added to their parents. Percentiles are nearest-rank;
percentiles across stages do not add up to the HTTP percentile.

Correctness verification
Every request must return HTTP 200, exact expected answer, grounded basis and
the expected source. Every request must execute retrieval and one mock call.
Prompt hashes must be identical across all requests within each run. Distinct
fixture IDs mean hashes need not match across fresh databases.
Independent NullPool verification, outside HTTP timings, checks ChatTurn JSON
equals the response, four messages exist (two initial plus two new), and stored
MessageEvidence equals the returned sources. Unique request IDs prevent replay;
real nonempty retrieval, grounded response and persisted policy rule out the
empty-context, built-in test-LLM, idempotency and insufficient-evidence paths.

Potential bottlenecks and limitations
First-run measurements identify retrieval, specifically its nested embedding
worker call, as the dominant measured component. Source retrieval.py:61 spawns
a worker for each call; index_worker.py:123 constructs TextEmbedding locally.
These code facts suggest process/model setup could contribute, but the timing
does not isolate loading from inference/IPC, so their individual costs are not
claimed. No optimization or causal performance fix is implemented.
Only one small corpus and short history, deterministic immediate LLM, sequential
requests, warmed database/model filesystem caches, and two local runs. Host
load/CPU frequency and Windows/WSL scheduling are uncontrolled. No concurrency,
throughput, cold-start benchmark, large-corpus behavior or real LLM latency.
P99 from 50 samples is the maximum; even the combined 100-sample P99 is a sparse
tail estimate, not a production SLO. Additional sampling is not a cure for an
uncontrolled host; retain both run distributions and time-order batch means.
