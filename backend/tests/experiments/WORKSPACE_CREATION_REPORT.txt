Verified Observations
- One deterministic run passed against PostgreSQL 16.15, using real loopback
  HTTP POST /api/workspaces and one Uvicorn server in one Python process.
- Dedicated new WSL cluster: /tmp/asteria-concurrency-20261016-unit1a/pgdata,
  port 55489, database workspace_concurrency_test. Exact data_directory,
  current_database and empty public schema checked before DDL/DML.
  No development database or real user data was used.
- One synthetic user and 99 seeded workspaces. A completed the real ORM COUNT
  (99) and paused in a test-only Query.count wrapper before returning to the
  production handler. The original document_slot remained held.
- Event order: A COUNT=99 -> B-held HTTP 429 -> independent DB count=99 ->
  release A -> A Commit -> A HTTP 200 -> DB count=100 -> B-retry COUNT=100 ->
  B-retry HTTP 409 -> DB count=100. Only new workspace name: A.
- A / B-held / B-retry had separate Session instances and initial PostgreSQL
  backend PIDs 468 / 469 / 473. All three reported read committed.
  B-held never reached the workspace COUNT checkpoint.
- Threading Events determine the interleaving; no sleep-based race injection.
  Checkpoint timeout 12s; HTTP timeout 8s; DB statement timeout 8s, lock timeout
  4s, connect timeout 5s; bounded server startup/shutdown waits.
- Production files and semaphore capacity unchanged. API stopped cleanly;
  dedicated PostgreSQL stopped with pg_ctl fast/wait. A later attempt to copy
  the PostgreSQL log found its /tmp path no longer available; stopped cluster
  retention is not established. Git changes consist only of experiment files.

Correctness Guarantees Under Tested Conditions
- With one API worker, this endpoint, independent request Sessions, READ
  COMMITTED, and no external writers, the forced overlap rejected B before
  its quota query while A owned the semaphore. A committed the 100th row and
  the subsequent attempt observed the committed quota and was rejected.
- This is bounded experimental evidence for the specified interleaving,
  supported by the existing lock scope; not a proof over all executions.

Unverified Limitations
- Multiple workers/hosts, external SQL/CLI writers, other isolation levels,
  crash/cancellation/connection-loss paths, and client retry after ambiguous
  commit were not tested. No stress, throughput or latency benchmark.
- NullPool intentionally separates DB connections; default pool behavior was
  not tested. The Session dependency is overridden to the isolated engine,
  with production autocommit=False/autoflush=False; auth, routing, gates,
  document_operation and create_workspace remain real production paths.
- Isolation/PID instrumentation adds read-only queries at Session creation.
  Commit logging delegates to the real Session.commit. The test does not
  replace PostgreSQL COUNT, INSERT or COMMIT, nor replace document_slot.
