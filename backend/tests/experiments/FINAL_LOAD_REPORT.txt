Asteria Phase 3 — Final Load Benchmark (2026-10-20)

结论
在本次受控突发负载下，新路径提高了成功率和成功吞吐，但仍有大量容量拒绝。
支持保持 Feature Flag 的受控、单 API Worker 试用；不足以支持默认全面启用或宣称容量上限。
本轮未修改生产代码、锁、容量、Supervisor、Recovery 或默认配置，未提交 Git。

Python 3.12.10、Windows 11（10.0.26300）；详细配置见 http/analysis.json 的 plan。
独立 WSL PostgreSQL 16.15，READ COMMITTED；隔离集群目录由外层脚本核对并清理。

本地 OpenAI-compatible Mock。Mock 自动固定等待 2 秒，无阶段放行屏障干预测量请求。
一个真实索引文档、固定问题及两条初始历史，每请求新建等价的已有 Session 和唯一 request_id。
同一合成用户/Workspace 下的独立 Sessions；不代表多租户隔离或不同文档规模。
连接池 size=5/max_overflow=10/timeout=30s；容量不变；Uvicorn 一个 Worker、limit_concurrency=16。
Session 等待 1 秒；仅后续异常回归切换为旧夹具的 0.15 秒，不混入性能样本。
并发级别 1、2、4，每模式每级别 10 轮，共 140 个测量请求。
每级别 AB/BA 交替，所有请求线程通过同一 Barrier 放行；不按服务执行阶段安排下一请求。
两模式各预热一次，测量期间复用同一模型进程，模式仅在上一批安全结束后切换。
HTTP 延迟从客户端创建前计时，包含独立 httpx Client 的构造和 TCP 请求。
这不是纯服务端耗时；Barrier 控制调用释放，不保证客户端初始化后 TCP 到达绝对同步。
客户端放行离散度见 analysis.json。线程与 OS 调度仍影响哪个请求通过 Embedding 门禁。
没有根据观察到的结果修改负载条件或追加更有利的错峰负载。

P95 判断
1/2/4 并发成功 P95 分别变化 +1.59%/-0.02%/+1.81%，未观察到大的尾延迟恶化。
但每组仅 10–14 个成功样本，nearest-rank P95 实际接近最大值；未给出统计显著性。
没有用户定义的 SLO，不能断言绝对约 4.0–4.5 秒一定可接受。
新旧成功集合不同，成功 P95 存在选择效应；已同时保留拒绝延迟和全量响应。

正确性与清理
全部 140 请求独立数据库连接验证：成功 Session Message=4、ChatTurn=1，回答一致且 Evidence
指向指定文档；拒绝 Session Message=2、ChatTurn=0，没有生成；Learning notes/revision 保持初值。
成功请求恰好一次 LLM，拒绝请求零次；Registry、Session Coordinator 与 Workspace Permit 退出后为空。
真实模型 HTTP 后置实验：同 Session 修改409、Session Delete409、Workspace Delete409；相同
request_id 同时调用返回同一持久化结果，仅一次生成。延迟约束 COMMIT 失败暂停 Rollback 时，
同 Session 和 Workspace Delete 仍409；释放后预期500，无部分持久化。新 Session 仍走排他旧路径。
独立 coordination 实验使用确定性测试模型验证 Learning 双向互斥、删除、独立 Learning 更新及异常清理；
不能将该部分标记为真实 FastEmbed 性能样本。
72 个 Provider Job 关闭时 active_processes=0，捕获进程句柄均确认退出；生产清理同时核验 Job
成员退出与 IPC 完成。Persistent Worker 最后 READY/restarts=0，正常关闭捕获成员均退出。
外层实验 Job total_processes=224、active_processes=0、日志线程停止。
完整 Backend 回归：303 项、198.811 秒，OK（跳过1项）；Ruff 与 git diff --check 通过。
生产 app 源码哈希在本轮前后完全一致。隔离服务已退出，PostgreSQL 已停止且集群目录已删除。最终清理状态以 evidence/final-load-01/result.json、regression.log 为准。

决策与未验证限制
本轮观察到小规模突发请求的成功率/吞吐改善，未发现持久化一致性回退。
但新路径在 2/4 并发仍有 40%/65% 拒绝，Embedding 单任务容量成为明确限制之一。
没有充分证据建议直接默认启用；保留 opt-in 更符合现有证据。真实 Provider、长历史、大文档集、
不同用户、多租户、长期稳态、持续到达流、真实网络延迟及系统饱和未验证。
仅单 API Worker，最多两路共享 Chat；不是四路成功生成或多 Worker 支持。
后续可讨论真实 SLO 和代表性到达流实验，但本轮不修改容量或实施优化。
