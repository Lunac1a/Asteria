Asteria Phase 3 / Unit 1 — Workspace quota row-lock fix
Date: 2026-10-16 (Australia/Sydney)
Base HEAD: 925c8bd6a91444fb63d8403c9a642775e67b658b; changes uncommitted.

Root cause and minimal fix
document_slot is process-local. Previously two processes could each COUNT 99
and commit one workspace, yielding 101. create_workspace now executes
SELECT users.id ... FOR UPDATE before COUNT. At READ COMMITTED, a request
waiting for that same user row runs its subsequent COUNT after the preceding
creator commits. COUNT, INSERT and COMMIT stay in the same transaction.
All exceptions inside this section, including quota HTTP 409, trigger explicit
rollback; the existing decorator still releases document_slot in finally.
If the user disappears after authentication, creation returns HTTP 401.

Production change: backend/app/api/routes/knowledge.py only. Existing semaphore,
session configuration, global isolation, indexing/chat/recovery concurrency and
deployment restrictions are unchanged. No new infrastructure or migration.

PostgreSQL observations (real HTTP, fresh dedicated cluster for each test)
PostgreSQL 16.15, actual READ COMMITTED recorded in each request.
Before: cross-process-unit1/result.json records COUNT 99/99, HTTP 200/200,
both INSERT/COMMIT successful, final count 101.
After / single-worker: B during A's pause returns 429; A returns 200; retry B
returns 409. Independent database snapshots: 99 -> 100 -> 100.
After / same-user: A pauses immediately after SELECT FOR UPDATE completes.
B attempts its own SELECT FOR UPDATE. pg_blocking_pids(B) contains A's actual
PostgreSQL backend PID. Neither request has COUNTed yet. After release,
A COUNT=99/HTTP 200; B COUNT=100/HTTP 409; final count 100.
After / different-users: A holds its user lock; process B locks its different
user row, COUNTs 99 and commits/returns 200 before A is released. A subsequently
returns 200; both users have 100 workspaces. This isolates DB row-lock behavior;
different users in the SAME process still share document_slot and can get 429.

Remaining limitations
This verifies only cooperating workspace creators using this User lock under
READ COMMITTED. Direct SQL/CLI writers that bypass the protocol can violate the
cap. SQLite does not implement this row-lock protection. Other isolation levels,
deadlock/connection-loss/crash schedules, fairness and throughput were not tested.
Database failures are rolled back and re-raised; no new retry/HTTP mapping or
production lock timeout was introduced. A commit followed by response failure
can still create client retry ambiguity. A full User FOR UPDATE lock can also
contend with updates or foreign-key checks involving that same user; this was
not broadened into a concurrency redesign.
These results do NOT make indexing, chat or recovery safe across workers and
do NOT remove Asteria's existing single-worker deployment restriction.
