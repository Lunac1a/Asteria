Asteria Phase 3 — Worker Lifecycle Isolation Experiment
2026-10-18 | Windows 11 10.0.26300 | Python 3.12.10

结论
在本机测试条件下，Job Object 能监管实际 FastEmbed 模型进程和其进程树：
正常关闭、监管父进程强制终止、模拟 Worker 卡死均完成清理，每种重复 3 次。
退出无法确认时，实验 Slot 保留并报告 DEGRADED，未放行新的 Worker。
这是隔离原型的证据，不是生产集成或任意 Windows 环境下的可靠性保证。

原型
windows_worker_job.py：创建 unnamed、不可继承的 KILL_ON_JOB_CLOSE Job。
CreateProcessW + STARTUPINFOEX 的 JOB_LIST 在进程创建时即绑定 Job，避免
先启动再 AssignProcess 的未监管窗口；HANDLE_LIST 仅传递三条标准流句柄。
没有复制 Job 句柄给观察者或 Worker，没有启用 breakaway，也没有兼容绕过。
实际 Worker 成功安装原内存限制 Job；本机嵌套 Job 组合实测可行。
worker_lifecycle_isolation.py：观察者启动独立监管进程；监管者独占 Job 句柄。
通过 ready/hold 消息同步，不靠 sleep 判断先后。观察者在故障注入前持有
各 PID 的 OS 进程句柄，利用 WaitForSingleObject 检查进程对象，避免 PID
重用误判。存活监管者还检查 Job ActiveProcesses=0 后才释放实验 Slot。
Slot 为隔离实验状态机，不是生产 document_slot，也未修改现有 Semaphore。

Verified Observations（final-02，共 12 个案例）
场景                         次数   清理耗时 Mean / Range (ms)
正常 stop + Job 剩余成员清理   3      155.17 / 149.61–164.85
强制终止监管父进程            3       40.74 / 30.10–46.64
模拟卡死 + 终止整个 Job       3      235.07 / 228.96–241.03
终止投递被抑制 + 最终清理     3      356.78 / 348.35–366.79

计时为 perf_counter 单调时钟。正常关闭从发送 stop 前开始；父进程死亡从
观察者调用 kill 前开始；卡死包含 200 ms 响应超时；终止超时包含对 3 个
进程各 100 ms 的退出等待。不可把后两行全部当成 OS 杀进程成本。

所有案例先完成真实 Embedding，384 维且全部有限；与前轮原 Disposable
reference_vector 最大绝对差均为 0。Launcher PID != 实际模型 PID。
每例 ready 时 Job 有 3 个活跃 PID，总计曾有 4 个进程；全部活跃 PID 的
进程句柄最终都 signaled，观察者读取线程退出；没有触发 emergency cleanup。
正常案例监管者 rc=0。卡死及终止超时的 Job 成员 exit_code=91。
父进程死亡案例监管者被 kill，成员退出码为 0；不把退出码 0 解释为正常
完成任务，关键证据是已接受 hold 后父进程死亡，随后全部进程对象退出。
监管者死亡没有 Python finally 清理；此路径由最后一个 Job 句柄关闭触发。
临时模型缓存已删除；没有残留测试服务或数据库资源。

重要发现与未验证限制
1. 旧“两 PID 已退出”并不等于 Job 已空：正常 stop 后即时观察到实际模型
   和启动器退出码均为 0，但 Job 尚有 1 个活跃成员。原型保留 Slot，尝试
   TerminateJobObject，再确认全部句柄退出及 ActiveProcesses=0。
   这可能只是后代退出时序；未证明该成员会永久孤立，也未将其称为泄漏。
   CIM 命令行查询被当前环境拒绝，错误保留在 JSON；具体进程角色未确认。
2. 首轮 job-01/job-02 正常关闭断言失败正是因剩余成员，记录保留。没有
   放松 Slot 释放条件；改为完整 Job 清理。job-03 四案例验证通过。
   job-final 首次加 CIM 查询时因查询不可用失败；改为记录诊断不可用后
   final-02 完成正式 3 轮。它是诊断权限限制，不是 Job 清理失败。
3. 终止超时是明确的故障注入：测试适配器抑制终止投递；OS 对活着的进程
   真实返回 WAIT_TIMEOUT=258、STILL_ACTIVE=259，Job ActiveProcesses=3。
   状态为 DEGRADED、slot_held=true、admission_allowed=false。
   随后恢复真实 Job 终止，仅在退出确认后释放。未复现内核无法杀死进程。
4. “卡死”是原测试 Worker 接受任务后有界等待 30 秒，忽略后续协议请求；
   不等同于内核不可中断 I/O、驱动故障、native 死锁或恶意进程逃逸。
5. 每类仅 3 次；未覆盖启动每一指令点的父进程死亡、观察者自身死亡、
   Windows 旧版本、服务账户、不同宿主 Job 限制、长时间运行或系统关机。
   JOB_LIST 要求 Windows 10 / Server 2016+；不支持时原型直接失败。
6. 资源回收证据是内核进程句柄退出、存活监管者的 Job accounting=0、
   协议线程退出和临时目录删除；没有测量系统 RSS 返回量或全系统句柄泄漏。

后续判断
Job 级所有权值得保留进入生产设计讨论，特别是同时确认后代进程退出。
仍需设计监督器故障状态、不可确认退出时的恢复流程、启动失败处理和
宿主限制兼容性；本轮没有接入生产、添加队列、重试或取消机制。
