Actual experiment configuration

QueuePool defaults observed on the actual experiment engine:
pool_size=5, max_overflow=10, pool_timeout=30s, recycle=-1,

No pool parameters were passed or changed. Test-only connection/statement/lock

Method
Fresh dedicated cluster on loopback 55489, database workspace_concurrency_test;
exact PGDATA/database name and empty schema verified before fixture writes.
One synthetic user, two initially empty workspaces, identical 63-byte document,
same app, engine, settings and stub result. A then B, sequentially. Schema/seed
warm-up checkouts are labeled null and excluded from request summaries.
One real Uvicorn server and real multipart HTTP upload route; get_db overrides
only the engine destination. Worker stub validates the input file and returns
the real {chunks: [{page, content, vector}]} interface, one fixed chunk.
No external provider, parser or embedding model was called. The 5s wait models
worker duration only; no delay is used to infer lifecycle ordering.
Pool checkout/checkin events and Worker/HTTP boundaries use perf_counter.
Every checkout is paired; overlap is computed from complete intervals.
Each request waits for explicit Session-finalizer completion before validation
and before starting the next request. HTTP timeout 15s; finalizer wait 5s;
outer experiment subprocess timeout 60s; bounded server startup/shutdown.

Verified Observations
Both HTTP responses were 200/ready with one chunk. Separate DB connections
confirmed ready state, chunk_count=1, exact content and vector persistence.
Pool checkedout() was zero at both Worker boundaries in both runs, and there
were no checkout intervals intersecting either Worker interval. Four checkout
intervals per request match pre-upload commit, pre-worker commit, post-worker
commit, and refresh/finalizer. No unexpected checkout was observed.
In this scenario, worker delay increased HTTP duration by about 5s without
extending connection checkout duration. This supports the explicit pre-worker
commit's intended connection-release behavior.

Unverified Limitations / design assessment
Returning to QueuePool means reusable, not physically disconnecting PostgreSQL;
an idle pooled database connection can remain open. The HTTP request, Session
object, synchronous endpoint thread and document_slot still exist during Worker
execution. This experiment proves no pool checkout retention in the tested
successful upload path, not that the whole request consumes no resources.
Only one ordered A/B pair, one small file, one stubbed chunk, and an otherwise
idle warmed pool were tested. No pool saturation/waiting, real embedding process,
large documents, cancellation, crashes, failed worker/commit, or multi-worker
behavior was tested. Timing precision does not establish stable performance.
The lifecycle design is consistent with releasing a scarce pooled connection
before slow indexing and reacquiring it for persistence. No optimization or
production change is proposed based on these observations.
